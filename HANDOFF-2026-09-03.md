## 5. Segurança

### 5.1 Três problemas encontrados e corrigidos — não desfazer

**1. PIN do dono exposto ao `anon`.** `set_owner_pin` e `verify_owner_pin` eram executáveis via `/rpc` com a chave pública. Qualquer um podia **redefinir o PIN** ou fazer força bruta. Revogados de `anon`, concedidos só a `authenticated`.

**2. `products.cost` vazava pelo cardápio.** RLS filtra **linha, não coluna**, e o cardápio precisa ler produtos. Resolvido com grant por coluna:

```sql
revoke select on public.products from anon;
grant select (id, store_id, category_id, name, description,
              price, unit, image_url, active, on_menu, sold_out,
              featured, sort_order, created_at) on public.products to anon;
```

> 🔧 Coluna nova em `products` nasce invisível ao anon — bom para dado sensível. Mas se o **cardápio precisar lê-la**, tem que entrar nesse grant, senão a query quebra com erro de permissão.

**3. `ingredients` e `recipes` com leitura pública.** A ficha técnica e o custo de cada ingrediente estavam legíveis por qualquer um com a chave pública. Policies removidas, `revoke all from anon`.

Além disso: `search_path` fixado nas funções pré-existentes, e as trigger functions com `revoke all from public, anon, authenticated` para não serem chamáveis por RPC.

### 5.2 Aberto — vale atenção

**Não existe separação de papéis.** Toda policy de escrita é `for all to authenticated using (true)`. Qualquer usuário logado é admin total: apaga produto, lê custo, mexe em venda. Com 2 usuários é gerenciável; se a loja ganhar login de atendente, vira problema. Caminho: tabela `profiles` com role + policies checando `auth.jwt()`.

**`menu_events` aceita insert anônimo sem limite.** É proposital (o cardápio precisa registrar), mas é vetor de inflação de métrica. Sem rate limit.

**Rodar `get_advisors` (security e performance) depois de qualquer mudança de schema.**

## 6. Painel admin (`voneis-painel.html`)

Arquivo único, sem build, Supabase JS via CDN. Feito para uso **no balcão, pelo celular**.

Três abas: **Cardápio · Painel · iFood**.

**Cardápio** — busca, chips por categoria + chip "Esgotados", lista agrupada. O botão **"Esgotou"** é a ação principal do dia: update otimista que muda na tela na hora e, se o request falhar, **desfaz e avisa** em vez de mentir que salvou. Editor em bottom sheet com nome, descrição, preço, custo com margem calculada ao vivo (vermelho abaixo de 30%), categoria, unidade, foto e os 4 toggles. Bloco de adicionais com toggle por grupo e botão **"Aplicar a toda a categoria"**. Gerenciador de adicionais separado, onde dá para desligar uma opção sozinha (acabou a calda de ninho no meio do dia).

**Painel** — vendido hoje/mês, esgotados agora, itens no cardápio, mais clicados, mais vendidos, margem por produto. **Vai ficar zerado** até o caixa ser usado e o cardápio entrar no ar.

**iFood** — campo do `ifood_merchant_id`, fila de mudanças com diff visual, e os botões de testar conexão / enviar / limpar fila.

Upload de foto passa por **resize em canvas para 900px, JPEG 0.82** antes de subir — foto de celular tem 4 MB. Manter.

## 7. Edge Function `ifood-sync`

Deployada, `verify_jwt: true`, usa o token do usuário logado (respeita RLS, sem service role). **Nunca executada** — falta credencial.

Secrets esperados: `IFOOD_CLIENT_ID` e `IFOOD_CLIENT_SECRET`, em Supabase → Edge Functions → Secrets. Ficam no servidor de propósito; nada disso pode ir para o HTML.

Ações: `ping` (autentica e lista lojas), `catalog` (lista catálogos, para mapear), `sync` (drena a fila; produto sem `ifood_item_id` volta como `sem_mapeamento` em vez de falhar calado).

- O portal do desenvolvedor existe e cria **aplicação de teste automaticamente** no cadastro
- A API de Catálogo tem método **PATCH** para "atualizar produtos já enviados, com o intuito de modificar uma informação específica do item **como por exemplo estoque e preço**"
- `Client ID` e `Client Secret` ficam na aba **Credenciais** da aplicação
- A loja é autorizada na aba **Permissões**, por ID ou CNPJ
- **Homologação é obrigatória** para acessar dados de loja em produção
- Existe rate limit por aplicação

### O que NÃO foi confirmado

**Os caminhos exatos dos endpoints.** Só as descrições apareceram na busca; a página de referência não foi aberta. As rotas no bloco `ROTAS`, no topo da função, são a melhor hipótese e **podem estar erradas**. Toda resposta de erro devolve o corpo cru do iFood no campo `detalhe`, justamente para corrigir rápido. **Validar contra a documentação atual antes de confiar.**

## 9. Armadilhas já pagas nesta sessão

**`list_tables` mente sobre contagem depois de restaurar projeto.** Reportou `rows: 0` em tudo quando havia 68 produtos — estatística de `pg_class` desatualizada. Isso levou a inserir duplicatas, que foram desfeitas por janela de `created_at`. **Sempre confirmar com `select count(*)` antes de tratar tabela como vazia.**

**Projeto restaurado demora a aceitar conexão.** `restore_project` retorna sucesso na hora, mas o Postgres leva dezenas de segundos. Uma migration aplicada nesse intervalo **retornou sucesso e não persistiu**.

**ES module não carrega em `file://`.** A primeira versão do painel usava `<script type="module">` com import de CDN; o Chrome bloqueia por CORS em origem `file://`, o script nunca rodava e o botão de login não fazia nada. Trocado por bundle UMD com `<script>` clássico. Hospedando na Vercel, módulo volta a funcionar.

**Erro genérico esconde a causa.** A tela de login dizia "e-mail ou senha não conferem" para qualquer falha — inclusive para "o script não carregou". Isso fez o cliente criar usuário novo à toa. Agora propaga a mensagem real do Supabase.
